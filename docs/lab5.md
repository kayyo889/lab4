# ЛР5. Continuous Integration

Для проекта Music Store используется GitHub Actions. При push и pull request запускается один и тот же workflow. Все проверки работают через изолированный Docker daemon в контейнере Docker-in-Docker на одноразовом GitHub-hosted runner. PostgreSQL тестов и базы для миграций и восстановления живут в отдельных Compose-проектах.

| Этап                  | Команда или результат                                                                 |
| --------------------- | ------------------------------------------------------------------------------------- |
| Зависимости           | `npm ci`, кэш загрузок по `package-lock.json`                                         |
| Линт и форматирование | `make quality`, отчёты ESLint и Prettier                                              |
| Тесты                 | `make migrate`, затем `make test` и JSON-отчёт Jest                                   |
| Миграции и бэкап      | `make db-check`, миграции на чистой БД и сверка данных в отдельной восстановленной БД |
| Безопасность          | Gitleaks, `npm audit`, Trivy. HIGH и CRITICAL блокируют выпуск                        |
| Контейнерная проверка | `make container-check` из ЛР4                                                         |
| Публикация            | Локальный registry в DinD и GHCR. Тег равен полному SHA коммита                       |

Отчёты в артефакте `ci-reports`. Задача публикации зависит от всех проверок и загружает ровно тот образ, который проверил Trivy. Она запускается только на push в `main`, `л5`, `л6` или `л7`. Для GHCR используется краткоживущий `GITHUB_TOKEN` с правом записи пакетов только в задаче публикации. Тестовые пароли генерируются отдельно для каждого запуска.

## Локальная проверка и защита

1. После `npm ci` на отдельной локальной БД выполните `make migrate`, `make verify`, затем `make db-check` и `make container-check` при запущенном Docker.
2. Откройте Actions для корректного коммита. Сверьте SHA тега и отчёты.
3. В отдельной демонстрационной ветке временно измените ожидаемое значение одного теста. Откройте PR в `л5` и покажите упавший Jest и пропуск публикации. Повторите с синтетическим тестовым секретом Gitleaks без действующих учётных данных.
4. В Settings → Branches или Rulesets для целевых веток с workflow включите PR, обязательный статус `DinD checks` и Code Owner review. Для действующей защиты назначьте в CODEOWNERS участника с правами записи, который сможет одобрять чужие PR. GitHub не позволяет одобрять собственный PR. Проверьте, что изменение Makefile, теста или workflow запрашивает согласование. Для `main` подключайте этот статус после появления workflow на ветке.
