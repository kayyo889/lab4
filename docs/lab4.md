# ЛР №4: контейнеризация и автоматическая проверка

## Структура и запуск на Linux VM

Dockerfile и Compose находятся в корне рядом с package-lock.json; `infra/nginx/`
содержит прокси, `scripts/` — эксплуатационные команды, этот документ — сценарий защиты.
Рекомендуемая ветка: `lab4/containerization`, затем PR в `main` с обязательным CI
`container-check`. В настройках защиты main администратор должен сделать этот check
обязательным: один workflow сам по себе не запрещает прямой push или ручное слияние.

Нужна Linux VM с Docker Engine, Compose v2 (поддержка `up --wait`), Make,
Python 3 и доступом к Docker Hub/npm при сборке. Для VM разумно выделить 2 vCPU,
2–4 GiB RAM и 20 GiB диска. Команды выполняются в клоне репозитория на VM:

```sh
cp .env.example .env
# Задайте в .env уникальный DB_PASSWORD (например, openssl rand -hex 24).
make container-check
make container-up
curl -i http://127.0.0.1:8080/health/ready
```

`container-up` повторно проверяет текущие файлы перед изменением основного окружения.
Перед деплоем отдельно проверяется и фактическая конфигурация с вашим .env.
Проверка сначала создаёт отдельный одноразовый проект; его изменение необходимо
для проверки кандидата и не является обновлением основной среды. При ошибке Make
не выполнит следующий шаг деплоя. Не обновляйте основное окружение напрямую через
`docker compose up`: такой ручной обход Make не защищён. CI выполняется на Linux
GitHub runner; для защиты также запустите команды на своей Linux VM.

По умолчанию наружу доступен только Nginx на loopback:8080. Для доступа извне VM
осознанно задайте `HTTP_BIND=0.0.0.0`, настройте firewall. Приложения и БД портов
на хост не публикуют. `backend` — внутренняя сеть, `frontend` принадлежит Nginx.
Процессы хоста/администратор Docker всё равно имеют административный доступ.

## Сборка и ограничения

Node, PostgreSQL и Nginx закреплены точной версией и SHA256 digest;
зависимости — package-lock.json и `npm ci --omit=dev`. Это фиксирует входы сборки,
но не обещает побитово одинаковый digest слоёв при разных версиях BuildKit.
Обновление зависимостей/базовых образов делается отдельным изменением с повторной
проверкой. Dockerfile копирует только необходимые пути, а .dockerignore использует
разрешительный список. `.env`, дампы, Git, тесты и локальные node_modules исключены.
Секреты нельзя добавлять в исходники, Dockerfile, ARG/ENV или публичные файлы;
Единственный разрешённый build-аргумент `APP_REVISION` содержит публичный номер
ревизии для OCI label, а не секрет. Пароль передаётся только в окружение запущенных контейнеров. Docker-администратор
может читать runtime environment — это не хранилище секретов для недоверенного хоста.

Запрещены `latest`, root, privileged/host network, отключение healthcheck,
публикация портов приложения/БД, встраивание секретов в образ. Проверка валидирует
Compose, контекст сборки и реально запущенные контейнеры; code review необходим
для выявления секретов, вручную вписанных в разрешённые исходники.

| Сервис            | RAM            | CPU  | PID | Причина                                                |
| ----------------- | -------------- | ---- | --- | ------------------------------------------------------ |
| app1/app2/migrate | 256 MiB каждый | 0.5  | 100 | Небольшое Express API, пул до 10 соединений на процесс |
| PostgreSQL        | 512 MiB        | 1    | 100 | Учебная БД и до 30 подключений, запас под миграции     |
| Nginx             | 64 MiB         | 0.25 | 50  | Прокси без дискового кеша                              |

Это стартовые лимиты, их уточняют по `docker stats` под реальной нагрузкой.
Миграционный контейнер завершается и постоянно ресурсы не потребляет.
Приложение работает под UID 1000, PostgreSQL — 70, Nginx — 101.
Приложение и Nginx имеют read-only filesystem и временный /tmp.

## Что проверяет make container-check

1. Политику конфигурации и сборку образа.
2. Готовность БД, однократные миграции, запуск двух приложений и Nginx.
3. Непривилегированных пользователей, healthcheck, отсутствие лишних портов.
4. Балансировку по заголовку `X-Instance-ID`.
5. Запись маркера в БД и его сохранение после `down/up` без `-v`.
6. Сборку с новой меткой APP_REVISION (проверяется изменение ID образа), новым
   тегом и пересоздание контейнеров через down/up, сохранение маркера.
   Это проверка обновления с остановкой, а не zero-downtime deployment.
7. SIGTERM, выход приложения с кодом 0 до истечения 20 секунд и работу второго узла.
8. pg_dump/pg_restore в отдельном проекте с новым volume и проверку данных/миграций.

Имена тестовых проектов уникальны. В `finally` удаляются только их контейнеры,
сети и volumes. Основной проект `music-store` не затрагивается. Образы остаются
в Docker cache. Проверка требует свободного места и не запускает seed с очисткой данных.

## Демонстрация на защите

```sh
docker compose ps
docker compose exec app1 id
docker compose exec app2 id
for i in $(seq 1 8); do curl -sD - http://localhost:8080/health -o /dev/null; done
make container-backup
# Сохраните запись через интерфейс; down не удаляет volume:
make container-down
make container-up
# Проверьте ту же запись в интерфейсе.
docker compose stop app1
curl -i http://localhost:8080/health/ready
docker compose ps -a app1
docker compose logs app1
make container-up
make container-restore BACKUP=backups/ИМЯ.dump RESTORE_PROJECT=restore-defense
# Проверка новой БД:
docker compose -p restore-defense exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM knex_migrations"'
```

Backup содержит всю БД, включая пользователей: храните его как секрет.
Restore отказывается использовать проект с существующим volume и не подключает
новую БД к рабочему приложению автоматически. Удалять `restore-defense` и его volume
можно только после проверки. `docker compose down -v` для основного проекта удалит данные.
Миграции выполняет сервис `migrate` после готовности БД; приложения ждут его успешного
завершения. Для ручного запуска: `docker compose run --rm migrate`.

## Масштабирование и отказоустойчивость

Nginx распределяет запросы round-robin между app1 и app2. При ошибке соединения
узел временно исключается (`max_fails=1`, `fail_timeout=5s`); запрос может быть повторён
на втором узле. Не включён `non_idempotent`: повтор уже отправленной операции записи
может создать дубль. Docker DNS переопределяется каждые 5 секунд после пересоздания узлов.
Healthcheck Docker показывает готовность, а Nginx OSS выявляет отказ пассивно по запросам.
При SIGTERM Node перестаёт принимать соединения, ждёт текущие запросы и закрывает пул
БД. Внутренний deadline 15 секунд меньше `stop_grace_period=20s`; аварийный выход — код 1.

Сессии уже находятся в общей БД, sticky sessions не нужны. Горизонтальное масштабирование
ограничивают общая БД (единственная точка отказа), число соединений (10 на экземпляр),
миграции схемы и конкурирующие записи. Будущие загрузки файлов и фоновые задания нельзя
держать только в памяти/локальном диске экземпляра; потребуются общее хранилище и очередь.
Nginx тоже остаётся единственной точкой отказа. Два приложения обеспечивают устойчивость
к отказу одного процесса приложения, а не к потере VM или БД. Для добавления третьего
экземпляра нужны сервис Compose и запись upstream; `--scale app1=2` здесь не используется.

## Переход со старого Compose (только PostgreSQL)

Новое окружение имеет явное имя проекта `music-store` и PGDATA в подкаталоге
`pgdata`. Оно не подхватывает автоматически volume старого проекта, в котором
PGDATA лежал в корне. Если в старом окружении уже есть данные, **до переключения**
сделайте `pg_dump -Fc` через старый Compose и сохраните его volume. Восстановите
дамп в новый пустой volume через описанную команду восстановления, проверьте данные
и только затем планируйте переключение приложения. Не переносите старую БД сменой
пути PGDATA и не удаляйте старый volume до проверки восстановления. Автоматический
тест сохранности проверяет обновления внутри новой конфигурации, а не этот переход.
